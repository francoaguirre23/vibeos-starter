# Global MINDSET Instructions

## Purpose
Maintain GLOBAL_MINDSET.md as the stable, cross-project model of how
decisions are made. This is the identity layer — it reflects patterns
proven true across multiple projects, not just one.

It is the highest-confidence layer in the cognitive stack.
It changes rarely and only with strong evidence.

## When to Use
- After completing ≥2 projects that each have their own project MINDSET
- Periodically (quarterly, or after a cluster of projects closes out)
- When you notice the same principle appearing in multiple project MINDSETs
- When a persona MINDSET entry feels like it belongs to you, not just the role

## Inputs
- GLOBAL_SIGNALS.md — the primary input; entries that meet promotion criteria
- All completed project MINDSET.md files (check "Open Promotions" sections)
- Persona MINDSET files (if a pattern has crossed from specialist into general)

## How to Update — Always Propose First

Never edit GLOBAL_MINDSET.md directly.

Step 1: Review GLOBAL_SIGNALS.md for entries with Confidence = High, Scope = Clearly general,
        and evidence from ≥2 project MINDSETs.
Step 2: Write a formal proposal using the format below.
Step 3: Review proposals — do they feel true across contexts, not just one?
Step 4: Apply only the ones that pass that test.
Step 5: Remove promoted entries from GLOBAL_SIGNALS.md.

---

## Proposal Format

Add proposals to a temporary section at the bottom of GLOBAL_MINDSET.md:

## Proposed Updates

Candidate:
<pattern — one clear statement>

Type:
Heuristic / Anti-pattern / Preference / Risk profile

Reason:
<why this generalizes beyond one project>

Evidence:
- Project: <name> — <1 line from that project MINDSET>
- Project: <name> — <1 line from that project MINDSET>

Source:
[self] or [persona-name] — who originated this pattern

Confidence:
Medium / High

---

## Promotion Criteria

Only promote a pattern to GLOBAL_MINDSET.md if ALL of the following are true:

- Appears in ≥2 project MINDSETs (not just SIGNALS or STANCE)
- Not tied to a specific tool, system, team, or one-off constraint
- Represents how decisions are made, not just what was decided
- Consistent across different project types and contexts
- Still feels true when you imagine a project you haven't done yet

If only one project supports it, leave it in that project MINDSET
and revisit after the next project.

---

## What Belongs in Global MINDSET

- Decision heuristics that apply regardless of project type
- Risk patterns that have shown up more than once
- Build preferences that reflect your actual defaults, not aspirations
- Problem framing approaches that worked across contexts
- Anti-patterns you keep having to consciously avoid

## What Does NOT Belong

- Project-specific lessons (keep in project MINDSET)
- Specialist craft knowledge (keep in persona MINDSET)
- One-off constraints or team-specific rules
- Patterns you hope are true but haven't tested
- Tool-specific behavior or stack choices

---

## Maintenance Rules

- Keep GLOBAL_MINDSET.md ≤100 lines
- No project-specific references in final entries
- No raw log entries or implementation details
- Prefer principles over examples
- Remove proposals section after applying accepted candidates
- If a global pattern is later contradicted by evidence, note it in
  a project STANCE before removing it — don't delete silently

---

## Promotion Flow Summary

```
Project STANCE
    ↓
Project SIGNALS
    ↓
Project MINDSET  ←  distilled at end of project
    ↓  flag in "Open Promotions → Global MINDSET"
Global SIGNALS  ←  staging area for cross-project candidates
    ↓  when pattern appears in ≥2 project MINDSETs
Global MINDSET  (via proposal format, not direct edit)
```

Persona MINDSET is a parallel track — specialist craft knowledge
that may occasionally surface a globally applicable pattern via
the same proposal process (stage in Global SIGNALS first).
